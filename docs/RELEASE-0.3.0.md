# 0.3.0 · 直接贴链接

> 发布日期：2026-10-28　｜　测试：273 项全绿　｜　新增依赖：无（yt-dlp 由用户自装，不打包）

---

## 一、这次变了什么

以前只能喂本地文件。现在可以直接给一条 C站（或任何 yt-dlp 支持的站点）链接：

```js
video_storyboard({ input: "https://example.com/video/BV1fq4y1u7nC" })
```

三个新能力：

| 能力 | 解决什么 |
|---|---|
| **两级取流** | 扫描用低清全片，细看回原始流取高清 —— 磁盘和时间都不浪费 |
| **`transcriptFile`** | 站点已有字幕时，整层 ASR 直接跳过 |
| **片源能力探测** | 下载前就知道"这条最高能到多少"，降级不再无声 |

## 二、怎么配（三步）

### 1. 装 yt-dlp

```powershell
pip install --user -U yt-dlp     # Windows
# brew install yt-dlp            # macOS
# pipx install yt-dlp            # Linux
```

脚本通常落在 `%APPDATA%\Python\Python3xx\Scripts`，**不在 PATH 上也没关系**——插件会自动去那里找，
或者用 `DSH_YTDLP_PATH` 指过去。

### 2. 导出 cookies.txt（可选，但建议）

```powershell
pip install --user yt-dlp
```

1. 浏览器装扩展 **Cookie-Editor**
2. 登录站点 → 点扩展 → Export → 选 **Netscape**
3. 存成 `bili-cookies.txt`，放到仓库外（比如 `~/.secrets/`）

> **为什么不能直接读浏览器**：Chromium 127+ 把 `SESSDATA` 用 App-Bound Encryption（`v20`）加密，
> 密钥绑定浏览器进程身份，任何外部程序都解不开。`yt-dlp --cookies-from-browser` 会报
> `Failed to decrypt with DPAPI`。这不是配置问题，是机制变了。

### 3. 写配置文件

**桌面版必须用文件，不要用 `setx`** —— DSH Desktop 读不到用户环境变量（ASR 那边已经踩过同一个坑）。

```json
// ~/.dsh/video.json
{
  "cookies": "D:/path/to/bili-cookies.txt",
  "scanHeight": 360,
  "zoomHeight": 1080
}
```

优先级：**工具参数 > 环境变量 > 配置文件**。

**完全不想配 cookie 也能跑**：插件会用匿名地址先探一次，够用就照常走。

## 三、实现方法

### 为什么是"下低清 + 取高清帧"，而不是"下完再分析"

因为这两件事的最优解相反。

**扫描要的是结构，不是像素。** 它的第一件事是把每帧缩到 64×36 再算 HSV —— 1920×1080 的
207 万像素，实际只用得上 2304 个。360P 的副本（5 分钟约 7 MB）和 1080P（108 MB）在扫描这一步
结果几乎一样，实测纯扫描 1.36 s vs 3.43 s。

**但取帧必须能随便跳。** `pick:"sharp"` 每格要 3 个候选帧，9 格就是 27 次随机 seek。
本地文件：9.6 s。走 HTTP：51.8 s。那 7 MB 是"后面随便跳"的入场费——所以低清那份必须落盘。

**高清只发生在 zoom。** 一次 2–6 帧，直接对原始流 `-ss` 取帧，**不落盘**。90 秒片子上
6 格 zoom 实测 5.3 s，回落 0 格。

```
URL
 ├─ 360P 全片落盘（7 MB）→ probe / scan / ASR / 取帧   ← 现有管线，零改动
 └─ 1080P 直链（只在内存，2 小时过期）→ zoom 时取帧，用完就扔
```

### 一次解析拿到所有需要的信息

`yt-dlp -J` 和 `-g` 一样快（2.4 s），但返回的是**完整格式表**而不是一个 URL。所以：

- 下载前就知道 `availableHeights` / `maxAvailable`，能提前判断"这条够不够高清"；
- 顺手把 zoom 要用的直链也挑出来存进进程内存，`video_zoom` 不用再解析第二次；
- 目标档位 `min(zoomHeight, maxAvailable)`，不会请求一个源根本没有的清晰度。

### 降级分三类，而不是一个 `degraded`

| 标记 | 含义 | 该做什么 |
|---|---|---|
| `source-max-720p` | 片子本身最高就 720P | 不用管 |
| `auth-limit` | 源有更高档，但当前身份拿不到 | 检查 cookie |
| `fetch-degraded-360p` | 请求成功但实际高度不符 | 重试；持续出现是 bug |

### 顺带修掉的两个清单缺陷

真实使用里，模型把"格的起点"当成"画面的时刻"，整段判断提前了 30 秒。两处都是我们的错：

- `alignCells` 把格内所有台词用空格 `join` 掉，**每条自己的时间戳全丢了**。现在只在真正有断点
  的地方（相邻句间隔 ≥ 1 s）插 `[10:09.4]`，不是每句都插——每句都插会吃掉 120 字预算的四分之一。
  格子同时带 `lines`（每句自己的 from/to）。
- 每格只写 `= 起止时间`，**从不说画面取自哪一刻**。`t_frame` 本来就在数据里，只是没渲染。
  现在输出 `frame@01:13.59`，**只在 `pick:"sharp"` 时**（mid 的帧位置可推导，sharp 的 3 选 1 推不出来）。

## 四、实测（90 秒片子，登录态）

| 环节 | 耗时 |
|---|---|
| `yt-dlp -J` 解析 | 2.4 s |
| 下载 360P 4.5 MB | 4.5 s |
| 扫描 + 9 格 | 9.1 s |
| 全流程（含 ASR） | 16.9 s |
| 全流程 + `transcriptFile` | **5.1 s** |
| 6 格 zoom @ 1080P | 5.3 s，回落 0 格 |

缓存之后（第二次看同一条）：**4.4 s**。

299 秒的片子冷缓存 10.8 s、热缓存 4.85 s——和 90 秒片子几乎一样，因为 27 次 ffmpeg 进程启动是常数。

## 五、已知限制

1. **匿名清晰度逐视频不同，无法预测。** 同一天测：`BV1BK411Q7ys` 匿名就有 1080P，
   `BV1fq4y1u7nC` 匿名只到 480P。所以不假定任何档位，只如实报告。
2. **直链约 2 小时过期。** zoom 前若过期会重解析一次；仍失败就回落低清并标 `frameFallbacks`。
3. **远程 zoom 只取 1 个候选帧**（本地是 3 个）。单次 HTTP seek 1.92 s，3 候选太重。
   转场附近可能有叠影——这是下一版要解决的（批量取帧）。
4. **没做标题卡/章节检测。** 实测 8 分钟动画片有 10 个黑场，9 个是 0.3–1.7 秒的转场。
   在没有正样本的情况下做检测器只会制造噪声，等有素材再说。
5. **URL 模式的 `--batch` 会丢 source 元信息**（batch 走本地路径以复用扫描结果）。

## 六、升级注意

- **不需要重新导出 cookie**，格式没变。
- **第一次跑会新建媒体缓存目录**：`tmpdir/dsh-video-storyboard/media`，上限 300 MB，超了按 mtime 从旧删。
  可用 `DSH_VIDEO_MEDIA_DIR` 换盘。
- **旧缓存仍然有效**：扫描/ASR 缓存的键没有变化，之前跑过的本地文件依然命中。
  只是媒体缓存对老版本没有（因为没有 URL 模式）。
- **`allowAnonymous` 语义变了**：以前是"允许匿名"，现在是"我知道是匿名，别提醒我"。
  匿名一直是允许的——早期那版硬拦被真实使用推翻了。
