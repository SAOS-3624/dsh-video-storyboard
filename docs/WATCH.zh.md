# 陪看配置（一起看电影）

> 这份文档只为了一件事：**让它稳定认出你在看什么、看到第几秒**。
> 配好一次，之后打开视频就行，不用贴链接、不用搜索。

---

## 一、为什么不配也能用，但会不准

Windows 的媒体控件（SMTC）会给"正在播放"的位置，但有三个毛病：

| 毛病 | 实测 |
|---|---|
| 只在事件时刷新 | 起播/暂停/拖动/切集才刷新，两次刷新隔过 **143 秒、216 秒** |
| 只给标题，不给地址 | 想拿视频必须靠标题去搜 |
| 很多播放器/网页根本不接 | 抖音、视频号常常完全不报 |

于是插件只能"猜"：拿标题去 B 站搜，再按时长核对。**猜不中就说不出话。**

---

## 二、开一个调试端口，这些问题就都没了

浏览器里的那个 `<video>` 元素知道**一切**：

```js
document.querySelector('video').currentTime   // 秒，毫秒级
location.href                                  // 页面地址 = 视频地址
```

插件通过 CDP（Chrome DevTools Protocol）读它，一次往返约 **20 毫秒**。

### 怎么开

**必须带 `--user-data-dir`（独立数据目录）** —— 这不是我们的偏好，是 Chromium 的硬限制：

> 用**默认 profile** 启动时，`--remote-debugging-port` **会被静默忽略**，端口不开。
> 实测：Edge 152 带参数启动、命令行里明明有 `--remote-debugging-port=9333`，
> 但 9333 一直没人监听；换成独立 `--user-data-dir` 立刻就有 7 个目标。

```bash
"C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe" ^
  --remote-debugging-port=9333 ^
  --user-data-dir="%USERPROFILE%/.dsh/edge-watch"
```

或者双击仓库里的 [`scripts/start-edge-debug.cmd`](../scripts/start-edge-debug.cmd)。

**也可以让插件自己起**（推荐，省得每次手动开）：

```jsonc
// ~/.dsh/video.json
{ "browserPort": 9333, "launchBrowser": true }
```

之后第一次调用 `video_watch` 时，如果端口没开，插件会自己把浏览器拉起来（独立 profile 那个窗口）。
默认关，因为不想在用户没同意的情况下随便开程序。

**这意味着：带端口的是一个独立窗口，和你平时那个 Edge 不是同一个。**
它有自己的 profile，所以**B 站要在这个窗口里登录一次**（之后会记住，cookie 存在
`~/.dsh/edge-watch`）。你平时那个 Edge 可以照常开着，两者互不影响。

**③ 告诉插件端口** —— 写文件（推荐）：

```jsonc
// %USERPROFILE%\.dsh\video.json
{ "browserPort": 9333 }
```

**④ 重启 DSH 一次**（插件树在进程启动时组合）。

## 三、三个必须知道的坑

### 1. 端口别用 9222

9222 是 Chrome DevTools 的惯例端口，**会被别的 Electron 应用占掉**。
实测这台机器上 WorkBuddy 自己就占着 9222，而且它的界面里**也有一个 `<video>`**——
盲连就会把宿主的界面当成你在看的片子。

插件默认用 **9333**，并且会跳过 `app.asar` / `devtools://` 这类页面。

### 2. 配置写文件，不要指望 `setx`

```bash
setx DSH_BROWSER_DEBUG_PORT 9333    # ❌ 对 DSH 桌面版无效
```

桌面版 DSH 的宿主进程 env 由启动器决定，`setx` 之后**插件仍然读不到**。
（ASR 的 key 也踩过一模一样的坑。）所以配置一律走 `~/.dsh/video.json`。

环境变量仍然认，只是排在文件后面。

### 3. 为什么"又开了一个 Edge"，而且没有登录态？

两层原因叠在一起：

1. **调试端口只能在启动时打开**，运行中无法开启（否则任何本机程序都能读你的页面）。
2. **默认 profile 不允许开端口**（见上一节），所以必须换一个 `--user-data-dir`。

结论：**开了端口的那个窗口，永远是另一个 profile。** 它没有你平时的登录态，
需要在这个窗口里单独登录一次（之后会记住）。公开视频不登录也能看。

> 之前文档里写"关掉现有 Edge 再带参数重启就行"，是错的——那样端口不会开。
> 实测过一次才改过来。

## 四、可变时段启动（ramp）

开头几批短、逐段加长、最后稳定：

```
1m → 2m → 3m → 4m → 5m → 5m → …
```

**为什么**：固定 5 分钟批次时，第一次开口要等到 5 分钟。用户刚点开视频，
最想要的是"它跟上了"这个确认。短批次让第一次反馈出现在 **45 秒**左右。

**代价**：起步那几分钟多算几段（每段 5–10 秒的 CPU），之后回到 5 分钟一档，
长期成本和固定批次一样。

```js
video_watch({ ramp: [30, 60, 120] })   // 更急的起步
video_watch({ segment: 300 })          // 稳定档（默认 5 分钟）
video_watch({ ramp: [] })              // 不要阶梯，全程等长
```

`video_watch({ statusOnly: true })` 里的 `batchPlan` 会告诉你当前用的是哪张表。

### 余量按**时间**算，不按段数

以前是"留两段"。问题是阶梯开头一段只有 1/2/3 分钟 —— **"两段"在最前面等于 2 分钟余量**，
比一次构建失败还短。现在按秒算：

```js
video_watch({ lookahead: 300 })   // 默认 5 分钟：当前位置之后要备好 5 分钟的内容
```

段短就自动多备几段：第 0 段（1 分钟）后面会连着备 2 分钟 + 3 分钟的两段，凑满 5 分钟；
稳定到 5 分钟一段之后，又回到"当前 + 下一段"。

**进入阻塞等待之前，这个窗口里的图会先建完**（同步，最多 4 段）。等待期间用户在看着，
没人能再建图 —— 所以"未来已就绪"是阻塞的前提，不是结果。返回文本里会写：

```
[buffer] 图已备到 03:12（3 段，约 5 分钟余量）。词就写这个区间：01:00–03:00、03:00–06:00
```

台词没有单独的余量：**词要覆盖的就是这个区间**，和图的余量同一个窗口。
词是模型写的（脚本只念），所以模型在阻塞前应该把这段窗口的 `at` 全排好。

只在本次就要交付（already due）时例外：那时不为了预取拖慢返回，改写后台串行建。
`video_watch({ prefetch: false })` 可以彻底关掉预取，只建当前段。

`statusOnly` 里 `depth` 会显示 `auto`（按时间算）还是一个数字（你显式给了 `depth`）。
`depth` 这个按段数的旧口径还留着，但**一般不要用**：它会让余量随段长缩水。

## 五、本地视频也能一起看

调试端口开着的话，**把本地文件拖进浏览器**就行：

```
source: browser-file → 记忆管理局 概念PV.mp4
watch 00:28 (browser, playing)
```

页面地址是 `file:///D:/...`，插件还原成本地路径直接当输入：
**不下载、不搜索、不问你要路径**，位置同样是毫秒级。

## 五点五、分工：模型写词，**别人**念词

```
模型（AI）                    插件核心                      接声音的那一方
─────────────                 ─────────────                 ──────────────
看画面 → 写台词 → 存队列      读位置 → 到点 → 交出台词  →     念出来（引擎自选）
保持 ≥ 5 分钟余量              没词就安静跳过（不骚扰）
有空时核对时间                 没人订阅就照旧叫醒模型
```

**台词永远是模型写的**；核心负责"在正确的时刻把它交出去"；
**念不念、用什么念、念多快，不归核心管**。

插件不带任何 TTS 引擎。想让它出声，接一个消费者：

```js
import { onSpeech } from 'dsh-video-storyboard/src/watch/voice.js';

onSpeech(({ state, text }) => { if (state === 'due') mySpeak(text); });
```

完整说明（事件字段、跨进程、现成适配器、最小适配器）见 README 的「接声音」一节。

- **有人订阅**：到点直接交给订阅者，循环**不叫醒模型**（0 token，也不会同一句说两遍）
- **没人订阅**：到点照旧叫醒模型，由模型自己说 —— 功能完整，只是安静
- 只做展示的订阅者（聊天框）必须传 `{ voice: false }`：否则循环会以为"有人会念"，
  从此不再叫醒模型，陪看会**默默地**变成哑巴
- `refillBelow`（**默认 0 = 关**）：想让它盯着库存再设；开着容易把模型叫得太频繁
- 没词时静默跳过，不会每 10 秒把你叫起来一次

### 每段写几句：不设默认值

固定成"每 10 秒一句"会把所有模型压成同一种语气。旋钮留在调用方：

```js
video_watch({ speakEvery: 10 })   // 每 10 秒叫醒一次（密一点）
video_watch({ speakEvery: 30 })   // 疏一点
video_watch({ refillBelow: 2 })   // 盯着库存，缺了就醒
```

## 五点六、模型为什么可以"空出来"

| 老做法 | 现在 |
|---|---|
| 模型阻塞等到点 → 输出一句 → 再次阻塞 | 脚本守着时间点，到点自己念 |
| 等待期间模型被占着，说下一句要干等 | 模型的时间全用来"看下一段、想说什么" |
| 每句都花 token | 念台词 **0 token**，只有"我自己想说的"才花 |

## 五点七、声音：核心只发事件

台词是提前写好的，让它"等到点再由模型输出一遍"是纯浪费：等待期间模型被占着，
输出还要花 token，而那些字早在几分钟前就定好了。

但**"不该由模型念"不等于"该由插件念"**。念台词要选引擎、装依赖、起子进程、管播放队列 ——
这些都是平台相关的实现细节。塞进一个通用的视频插件里，代价是具体的：
Linux / 容器里也带着一段 Windows 专用代码、和宿主已有的语音插件抢同一句话、
想换音色就得改插件。

所以现在的边界是：

```
插件核心：读位置 → 到点 → 把 { at, text } 交出去       （守时在这里，0 token）
消费方：  收到 → 用你选的引擎念出来                     （引擎在那里，插件不管）
```

```js
// 消费方（companion 插件 / 宿主 speech service / 你自己的脚本）
import { onSpeech } from 'dsh-video-storyboard/src/watch/voice.js';
onSpeech(({ state, text }) => { if (state === 'due') mySpeak(text); });
```

- **没人订阅**：到点照旧叫醒模型，由模型自己说 —— 功能完整，只是安静
- **有人订阅**：循环不再叫醒模型，同一句不会被说两遍
- 插件里**没有任何引擎代码**，也没有 `tts` / `voice` / `rate` / `listVoices` / `speakAloud` 这些参数
- 事件在被投递时**已经到点了**：守时仍由核心做（每 2 秒读一次真实播放位置），
  订阅者收到就念，不用自己盯时间轴；`at` 留给需要校准或淡入淡出的实现

想要开箱有声，装一个适配器就行（`~/.dsh/voice.json` 写一行路径）：

```json
{ "adapter": "D:/deepseek/3-Life/dsh-video-storyboard/examples/voice-edge-tts/index.mjs" }
```

`examples/voice-edge-tts` 是现成的：edge-tts 合成 → `ffplay` 播放 → 失败退回系统声音，
而且每条台词都会在 stderr 打一行 `[voice 03:11.4] …` —— 调时序时这行比声音有用。

## 六、两种等待方式：定时唤醒 vs 阻塞等待

插件支持两条路，**互相独立**：

| | 定时唤醒（默认） | 阻塞等待 `wait: true` |
|---|---|---|
| 原理 | 后台每 2 秒比对，到点 `sessionController.prompt()` 投一条消息 | **这一次调用一直挂着**，到点了工具自己返回 |
| 依赖 | 宿主的唤醒接口 | **不依赖任何宿主接口** |
| 代价 | 接口不通就静默失败 | 等待期间会话被占着，用户插话要等它返回 |
| 上限 | — | `maxWaitSec`（默认 180，最大 600） |

**为什么会有第二种**：阻塞等待就像等 npm 上传结果——进程挂着，结果回来了自然就继续了，
对话根本没断过。它绕开了"叫醒"这一环，所以在那条路没验证通之前，它更可靠。

```js
video_watch({ wait: true, maxWaitSec: 300 })   // 一直等到该说话，再返回
```

暂停 / 倒回 / 到封顶都会让它提前返回，不会死等。

### B 站字幕：登录一次，之后不用管

B 站的字幕是**单独轨道**，只有登录用户能读。插件现在会：

1. 先用配置里的 cookie 试
2. 不行就直接 **从带端口的浏览器里读 cookie**（CDP `Storage.getCookies`），转成 yt-dlp 的格式
3. 还不行就退回 ASR，并在清单里写明"这视频有字幕，但要登录"

所以你要做的只有一件事：**在带端口的那个窗口里登录一次 B 站**。

自检：

```js
video_watch({ checkCookies: true, input: "https://www.bilibili.com/video/BV..." })
```

返回 `login.isLogin` 和 `subtitles.ok`。

**还没打开视频？** 用 `waitForVideo` 让它等着：

```js
video_watch({ waitForVideo: true, maxWaitSec: 120 })
```

调用方（模型）**必须先说一句"我在等你打开视频"**——工具阻塞期间说不出话，
不说这一句，用户只会看到长时间的沉默。

## 七、不用 AI 时会不会有开销

| 状态 | 开销 |
|---|---|
| DSH 没开 | **零**（插件不运行） |
| DSH 开着、没在陪看 | **零**（没有循环、没有轮询） |
| 陪看中 | 每 2 秒一次**本地**比较（纯算术）；每 15 秒读一次位置（CDP ≈20 ms，SMTC ≈1 s） |
| 浏览器带端口开着，但没在陪看 | 接近零（只是端口在监听，没有连接就没有流量） |

**会不会忘了关？** 不会一直转下去，有四个自动停：

```
视频播完        → 停（video-ended）
换片了          → 停（video-changed，等下一次重新开始）
读了 10 分钟没有可信位置 → 停（position-unreadable），中途会先问你一次
浏览器/SMTC 都没源 5 分钟 → 停（no-source）
```

想手动停：`video_watch({ stopLoop: true })`。

## 八、排查

```js
video_watch({ statusOnly: true })
```

返回里看两个字段：

- `confidence`：`browser`（最准）/ `fresh` / `extrapolated`（推算）/ `unknown` / `none`
- `reason`：为什么没说 —— `not-due` / `extrapolated-not-confirmed` / `paused` / `position-unknown` …

`confidence: smtc` 之外的 `extrapolated` 说明端口没开，正在靠推算。想稳就按第二节配一次。
